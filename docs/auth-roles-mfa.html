Roles y Autenticación en dos pasos

Modelo de permisos de tres niveles (Admin / Socio / Asociado) y verificación TOTP opcional con gate en el proxy de Next.js 16.

Backend · NestJS Frontend · Next.js 16 Auth · Supabase TOTP MFA Base de datos · RLS PostgreSQL Migración 23 11/11 pruebas ✓

Resumen

La aplicación manejaba dos roles implícitos (user / viewer). Esta release los reemplaza por un modelo de tres niveles alineado con la estructura real de un estudio jurídico: un administrador de sistema, socios que ven toda la cartera del estudio, y asociados que ven únicamente sus propios expedientes.

Se agrega además soporte de segundo factor TOTP (Google Authenticator, Authy, etc.). El MFA es opcional en el MVP — los usuarios sin factor configurado reciben un aviso persistente en el header, pero no quedan bloqueados. Cuando un usuario configura el factor, el gate en proxy.ts intercepta el primer login e impide el acceso a cualquier ruta hasta completar la verificación.

Los tres roles

Nivel 1

Admin

  • Acceso completo a toda la plataforma
  • Único que puede otorgar o revocar rol Admin
  • Ve todos los expedientes del estudio
  • Gestiona usuarios desde /settings/users
  • Accede a /admin
Nivel 2

Socio

  • Ve todos los expedientes del estudio
  • Gestiona usuarios (puede asignar Socio / Asociado)
  • No puede otorgar ni revocar rol Admin
  • No puede cambiar su propio rol
  • No accede a /admin
Nivel 3

Asociado

  • Ve solo expedientes donde es creador o responsable
  • Sin acceso a /settings/users
  • Sin acceso a /admin
  • Puede gestionar su propia seguridad
Migración de datos: los roles anteriores 'user' y 'viewer' fueron migrados automáticamente a 'asociado'. El default de nuevos usuarios es 'asociado'.

Implementación en base de datos (RLS)

El control de acceso por rol se implementa en PostgreSQL a través de Row Level Security. La migración 23 introduce dos funciones SECURITY DEFINER que sirven como punto de verdad único y evitan la recursión 42P17.

has_firm_wide_access()

Retorna true si el usuario autenticado es admin o socio. Determina visibilidad firma-completa.

select exists (
  select 1 from public.users
  where id = auth.uid()
    and role in ('admin','socio')
);

can_access_case(cf_id uuid)

Punto de acceso único para todas las políticas de expediente. Cubre los tres casos: creador, responsable, o acceso firma-completa.

select exists (
  select 1 from public.case_files cf
  where cf.id = cf_id
    and cf.deleted_at is null
    and (
      cf.created_by = auth.uid()
      or cf.responsible_attorney_id = auth.uid()
      or public.has_firm_wide_access()
    )
);
Por qué SECURITY DEFINER: sin este atributo, la función que consulta public.users para leer el rol dispara la misma política RLS sobre users, que a su vez consulta el rol — recursión infinita (error 42P17). Con SECURITY DEFINER la función corre como su dueño (postgres), que bypasea RLS, cortando el ciclo. El mismo patrón ya existía en is_admin() de la migración 12.

Gestión de usuarios

La pantalla /settings/users lista todos los usuarios del estudio y permite a admin y socio cambiar roles. El servidor evalúa el rol del actor antes de renderizar — un asociado que accede directamente a la URL ve un estado vacío de "sin acceso", no un error.

Endpoint de cambio de rol

PATCH /users/:id/role
Body: { "role": "admin" | "socio" | "asociado" }
Requiere Authorization: Bearer <jwt>. El UsersService verifica tres reglas antes de actualizar:
  • Solo admin o socio pueden llamar al endpoint (403 si es asociado)
  • Nadie puede cambiar su propio rol (400)
  • Solo admin puede otorgar o revocar el rol admin (403 si es socio)

Autenticación en dos pasos (TOTP)

Se usa el MFA nativo de Supabase Auth. El factor es TOTP (Time-based One-Time Password), compatible con Google Authenticator, Authy, 1Password y cualquier app que soporte RFC 6238.

Niveles de garantía (AAL)

AAL1

El usuario completó solo la contraseña. Estado por defecto en todo login. Si el usuario no tiene factor configurado, permanece en AAL1 indefinidamente sin restricciones adicionales.

AAL2

El usuario completó contraseña + código TOTP. Requerido cuando el JWT indica nextLevel = 'aal2', es decir, cuando existe un factor TOTP verificado en la cuenta.

Cómo sabe el servidor si hay factor: aal.nextLevel === 'aal2' significa que el usuario tiene un factor TOTP verificado asociado a su cuenta. aal.currentLevel === 'aal1' significa que este login en particular todavía no lo completó. Ambos valores vienen de los claims del JWT — no hay llamada de red adicional.

Flujo de enrollment

1 — Usuario abre /settings/security
El server component consulta mfa.listFactors(). Si no hay factores TOTP verificados, muestra el banner de advertencia y el botón "Activar verificación en dos pasos".
2 — Click en "Activar"
El client component llama mfa.enroll({ factorType: 'totp' }). Antes de enrollar, elimina cualquier factor no verificado previo para evitar el error "duplicate friendly name".
3 — QR y código secreto
Se muestra el QR para escanear con la app de autenticación y el código en texto plano como respaldo. El usuario ingresa el código de 6 dígitos generado por la app.
4 — Verificación
mfa.challengeAndVerify({ factorId, code }). Si es correcto, el factor queda en estado verified. El JWT del usuario ahora tiene nextLevel = 'aal2'.
5 — Activación confirmada
El banner de advertencia desaparece del header. En el próximo login, el sistema requerirá el código TOTP antes de dar acceso a cualquier ruta.

Gate en proxy.ts (Next.js 16)

En Next.js 16 el middleware se llama proxy.ts (no middleware.ts) y exporta una función proxy. El gate se coloca aquí y no en el layout de (protected) porque las route handlers de /api/* no pasan por el layout.

// proxy.ts — fragmento relevante
if (user && !isPublicRoute(pathname) && pathname !== MFA_VERIFY_ROUTE) {
  const { data: aal } = await supabase.auth.mfa.getAuthenticatorAssuranceLevel()
  if (aal?.currentLevel === 'aal1' && aal?.nextLevel === 'aal2') {
    const verifyUrl = new URL(MFA_VERIFY_ROUTE, request.url)
    verifyUrl.searchParams.set('redirectTo', pathname)
    return NextResponse.redirect(verifyUrl)
  }
}

Página de verificación — /mfa-verify

Ruta pública (no requiere AAL2 para acceder). El server component verifica que el usuario esté logueado, que no haya completado AAL2 ya, y que tenga un factor verificado. Si alguna condición no se cumple, redirige a /dashboard. El client component acepta el código de 6 dígitos y llama mfa.challengeAndVerify(); en caso de éxito redirige al destino original vía el param redirectTo.

Desactivar MFA

El botón "Desactivar" en /settings/security llama mfa.unenroll({ factorId }). El factor queda eliminado de la cuenta, nextLevel vuelve a 'aal1', y el gate deja de interceptar futuros logins.

Indicadores visuales

Badge de rol en el header

Chip pequeño junto al avatar que muestra ADMIN, SOCIO, o ASOCIADO. El valor viene del server component del layout que consulta public.users.

Banner de MFA en el header

Si mfaEnabled === false (sin factor TOTP verificado), aparece un aviso persistente con link a /settings/security. Desaparece en cuanto el usuario activa el factor.

Sidebar adaptativo: los ítems del sidebar se filtran según el rol. "Usuarios" solo aparece para Admin y Socio. "Administración" solo para Admin. "Seguridad" es visible para todos los roles. La lógica vive en constants/navigation.ts — cada ítem tiene un campo roles?: readonly Role[]; ausente significa visible para cualquier rol autenticado.
