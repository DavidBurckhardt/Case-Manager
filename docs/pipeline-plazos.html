Pipeline de Ingesta y Motor de Plazos

Cómo un archivo PDF pasa de la pantalla de carga a un expediente estructurado con plazos judiciales calculados automáticamente.

Backend · NestJS Mensajería · NATS JetStream LLM · Claude API Storage · Supabase 2 fases En producción

Resumen

El usuario arrastra uno o más documentos (PDF, imagen, DOCX) al área de carga. En segundos aparece un expediente marcado como "procesando". En el background, un worker descarga los documentos, los envía directamente al LLM, y estructura toda la metadata del expediente: carátula, juzgado, actor, demandado, datos del accidente, diagnósticos, y — lo más crítico — los actos procesales que disparan plazos judiciales.

El pipeline tiene dos fases deliberadamente separadas: la Fase 1 responde en milisegundos para no bloquear al usuario, y la Fase 2 corre de manera asincrónica a través de una cola NATS JetStream con redelivery automático.

Flujo completo de procesamiento

1a
Upload al storage
POST /documents/upload — multipart/form-data, campo files, hasta 20 archivos por request. El endpoint acepta PDF, JPG, PNG, DOCX (hasta 25 MB cada uno por defecto, configurable con MAX_DOCUMENT_SIZE_MB).

Cada archivo pasa por validación de tipo MIME y tamaño. Si pasa, el service calcula un SHA-256 del contenido para deduplicación: si el mismo usuario ya subió exactamente el mismo archivo antes, se reutiliza el objeto en storage sin re-subir — solo se crea un registro nuevo en case_file_documents apuntando al storage_key original. 
// storage key: inbox/{userId}/{documentId}.{ext}
buildInboxKey(userId, documentId, ext)
1b
Creación del expediente placeholder (Fase 1)
Todos los archivos del batch se agrupan en un solo expediente. El service crea inmediatamente un case_file con número de borrador (BORRADOR-{fecha}-{uuid}), processing_phase = 'analyzing', y estado inicial INICIADO. Los documentos quedan vinculados al case via case_file_id.

Esta respuesta ya incluye el caseId → el frontend puede redirigir al usuario a la ficha del expediente aunque la extracción todavía no terminó.
1c
Enqueue del job de extracción
Se publica un único mensaje extract.request en NATS JetStream con el caseId y la lista de documentos. El stream usa RetentionPolicy.Workqueue: el mensaje persiste hasta que el consumer lo acknowledges exitosamente. Si el API se reinicia antes del ack, el mensaje se reentrega automáticamente. 
// contracts.ts
interface ExtractRequest {
  jobId: string
  caseId: string
  documents: Array<{
    documentId: string
    filename:   string
    mime:       string
    storageKey: string
  }>
}
2a
Consumo del job — idempotency check
El PipelineService consume el mensaje y verifica que el case sigue en processing_phase = 'analyzing'. Si ya está en complete o preview (procesado por una entrega anterior), el job es un no-op y se ackea para evitar loops. Los tipos MIME no soportados por el LLM (por ahora todo lo que no sea PDF o imagen) se marcan con processing_error en el documento y se omiten.
2b
Extracción LLM (Fase 2)
Los documentos se descargan del storage como raw bytes y se envían directamente al LLM — sin OCR intermedio. El LLM recibe los PDFs e imágenes como adjuntos multimodales y devuelve un único JSON con toda la estructura del expediente.

El system prompt instruye al LLM con 10 reglas de normalización (fechas en YYYY-MM-DD, CUIT sin separadores, montos numéricos, prioridad judicial sobre administrativa) y una sección crítica sobre actos procesales — es lo que alimenta el motor de plazos. 
// Ventana de ack: 15 minutos (batch de PDFs pesados puede demorar)
ACK_WAIT_NS = 15 * 60 * 1_000_000_000
MAX_DELIVER = 4  // reintentos antes de DLQ
2c
Enriquecimiento del expediente
El JSON extraído se valida con Zod (extractedCaseSchema) — campos inválidos o con tipo incorrecto se coercionan a null en lugar de fallar el parse completo. Luego se actualizan las tablas satélite del expediente: 
case_file_plaintiff        — actor
case_file_accident         — datos del accidente
case_file_medical          — diagnósticos, tratamientos
case_file_insurance        — aseguradora (ART)
case_file_employer         — empleador
case_file_admin_proceedings— trámite ante comisión médica
case_file_parties          — demandados + abogados
Para el número de expediente se intenta asignar el extraído por el LLM. Si ya existe (caso de re-upload del mismo expediente), se prueba con sufijo: 17236 (1), 17236 (2)… hasta 50. Finalmente processing_phase pasa a 'complete'.
2d
Generación de plazos
Inmediatamente después del enriquecimiento, se llama a DeadlinesService.generateForCase() con la lista de procedural_acts extraídos. Este paso genera los plazos judiciales y persiste el estado 'complete' aunque falle.

Estados de processing_phase

EstadoQué significaQué ve el usuario
analyzing El LLM está procesando. Fase 1 completada, Fase 2 en progreso. Badge animado "Procesando" en la lista y en la ficha.
complete Extracción exitosa. Toda la metadata está disponible. Ficha completa con todos los campos.
preview La extracción falló (LLM error, sin archivos legibles) o no hubo documentos soportados. El expediente existe pero sin metadata. Ficha vacía, mensaje de error visible.
Recuperación de huérfanos: al arrancar el API, el ProcessingService busca expedientes en estado analyzing con updated_at más viejo que 30 minutos y los resetea a preview. Esto evita que un caso quede pegado en "Procesando" para siempre si el API se cayó en medio de una extracción.

Extracción de metadata — LLM

Schema extraído

El LLM devuelve un único JSON que el sistema valida con Zod. Cada sección cubre una entidad del expediente:

Expediente

  • case_number — único requerido
  • title, court, jurisdiction
  • department, process_type
  • legal_matter, status
  • filing_date, claim_amount

Actor / Partes

  • plaintiff: nombre, DNI, CUIL, nacimiento, domicilio
  • defendants[]: nombre, tipo, CUIT
  • lawyers[]: nombre, matrícula, a quién representa

Contexto médico-laboral

  • employer: empresa, CUIT, actividad
  • insurance_company: ART, CUIT, NRO siniestro
  • accident: fecha, lugar, mecanismo
  • medical: diagnósticos, tratamientos, incapacidad
  • administrative_proceedings: comisión médica

Actos procesales

  • document_type: CEDULA | SENTENCIA | PROVIDENCIA | OFICIO | ESCRITO | DEMANDA | OTRO
  • act_type: uno de 8 valores predefinidos o null
  • document_date: fecha del documento
  • notification_date: fecha de notificación — desde acá corre el plazo
  • description: descripción en español

Otros campos

  • legal_claim: monto pedido, argumentos legales, desafíos constitucionales
  • important_dates[]: lista de fechas relevantes con descripción
  • documents_detected[]: tipos de documentos encontrados
  • summary: resumen factual en español, máx 250 palabras
notification_date vs document_date: el LLM distingue explícitamente entre la fecha impresa en el documento y la fecha en que la parte fue notificada (p.ej. la fecha de diligenciamiento de la cédula). Los plazos judiciales corren desde la notificación — usar document_date correría el plazo un día antes. Si el LLM no puede determinar la notification_date con seguridad, devuelve null y el motor de plazos omite ese acto.

Motor de plazos (DeadlinesService)

Recibe los procedural_acts extraídos por el LLM y genera automáticamente los plazos judiciales. Corre como último paso de la Fase 2 — si falla, el expediente igual queda en complete (los plazos no bloquean la extracción).

Algoritmo de conteo — Art. 156 CPCCN

El día de la notificación no se cuenta. El conteo arranca al día siguiente, y el primer día hábil posterior es el día 1 (no el día 0). Los días inhábiles (fines de semana + feriados judiciales + feria enero/julio) se saltan.

// Ejemplo: notificación 30/04/2026 (jueves), plazo 5 días hábiles
// 01/05 feriado → 02-03/05 fin de semana
// Día 1: lunes 04/05 · Día 2: martes 05/05 · Día 3: miércoles 06/05
// Día 4: jueves 07/05 · Día 5: viernes 08/05
// → fecha_vencimiento: 2026-05-08
HolidaysService: los feriados judiciales se leen de la tabla judicial_holidays en Supabase y se cachean en memoria por año. Si la consulta falla (red, RLS), el service retorna un Set vacío y continúa — el plazo se calcula sin feriados antes de fallar el pipeline entero. El cache vive mientras el proceso corre; se invalida solo con un restart.

Deduplicación de actos

El LLM puede extraer el mismo acto de páginas duplicadas. El motor de plazos deduplica por clave (act_type, notification_date) antes de insertar. También borra los plazos auto-generados anteriores antes de insertar los nuevos — si el expediente se re-procesa, los plazos se recalculan limpios. Los plazos marcados con is_auto_generated = false (creados manualmente) no se tocan.

Alertas de vencimiento (AlertsService)

Un cron corre diariamente a las 8:00 AM y chequea todos los plazos en estado PENDIENTE. Para cada plazo calcula los días hábiles restantes y dispara alertas según umbrales.

Umbrales y canales

UmbralDías hábiles restantesCanalImplementado
T-10 ≤ 10 In-app (notificación UI) Registrado en DB, UI pendiente
T-5 ≤ 5 Email via Resend ✅
T-2 ≤ 2 Email urgente via Resend ✅
T-0 = 0 (vence hoy o vencido) Bloqueo visual en UI Registrado en DB, UI pendiente

Idempotencia y deduplicación de alertas

Cada alerta disparada se registra en la tabla deadline_alerts con clave (deadline_id, alert_type). En la siguiente corrida del cron, esa combinación se excluye — el mismo email no se manda dos veces. Si el cron estuvo caído varios días y varios umbrales se cruzaron a la vez, se registran todos pero solo se envía el más urgente para no mandar una ráfaga de emails viejos.

Email de alerta

El destinatario es el responsible_attorney_id del expediente, con fallback al created_by. El email incluye: descripción del plazo, número de expediente, carátula, fecha de vencimiento, días hábiles restantes, y un link directo a la ficha. El asunto usa 🚨 para T-2 y ⚠️ para T-5.

Variables de entorno requeridas: RESEND_API_KEY y RESEND_FROM_EMAIL. Si alguna falta, el service loguea un warning y omite el email sin fallar. APP_URL configura el dominio del link en el email (default: http://localhost:3000).

Endpoint de prueba

POST /deadlines/alerts/run
Dispara el chequeo de alertas a demanda sin esperar el cron de las 8am. Requiere rol admin. Responde { checked: N, sent: M }. Idempotente — correrlo dos veces seguidas da sent: 0 en la segunda.

Referencia de API

POST /documents/upload
Multipart/form-data. Campo: files (1–20 archivos). Formatos: PDF, JPG, PNG, DOCX. Límite por archivo: MAX_DOCUMENT_SIZE_MB (default 25 MB).
Respuesta: { documents: DocumentRow[], errors: { file, error }[] }.
Requiere Authorization: Bearer <jwt>.
GET /processing?limit=50&include_terminal=false
Lista de documentos procesados, ordenados por fecha de carga descendente. Incluye join a case_files para mostrar estado del expediente.
include_terminal=false (default) excluye documentos con ERROR. Los documentos COMPLETED no se excluyen aunque el case esté en analyzing — el badge de la UI lee processing_phase del expediente.
Requiere Authorization: Bearer <jwt>.

Gaps vs PRD MVP

T-10 in-app y T-0 bloqueo visual no implementados: el PRD especifica cuatro umbrales de alerta. T-5 y T-2 con email están completos. T-10 y T-0 se registran en deadline_alerts para trazabilidad pero no disparan ninguna acción en la UI todavía. Pendiente: banner in-app para T-10 y overlay/bloqueo visual para T-0.
Campo "confianza" eliminado: el PRD menciona que extracciones con confianza < 0.7 se marcan para revisión humana. Este campo fue eliminado deliberadamente porque el LLM evaluaba su propia confianza sin criterio objetivo externo — no hay ground truth con qué comparar. Decisión: el usuario humano revisa la ficha y corrige si es necesario.
Ingesta por email: el PRD incluye un canal IMAP como v1.0, no MVP. El sistema actual es solo carga manual. El flujo está diseñado para extenderse: el DocumentsService ya soporta origin: 'EMAIL' en el schema.
