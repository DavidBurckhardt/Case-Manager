Ciclo de Vida del Expediente

State machine judicial sobre el proceso CPCCN para el Generador de Expedientes. Implementa transiciones automáticas por pipeline e historial de auditoría con control de acceso por rol.

Backend · NestJS Frontend · Next.js 16 Base de datos · Supabase (PostgreSQL) Migración 24 7/7 pruebas ✓

Resumen

Cada expediente judicial tiene un estado procesal que avanza conforme a las reglas del CPCCN. Esta feature reemplaza los 11 estados genéricos en inglés por 13 estados en español con el proceso judicial argentino real, agrega un grafo de transiciones válidas, y registra en auditoría cada cambio de estado indicando si fue automático (disparado por el pipeline de IA) o manual (acción de un usuario con justificación).

Los expedientes ya existentes en la base fueron remapeados automáticamente a sus equivalentes en español durante la migración, sin pérdida de datos.

Referencia de API

GET /workflow-states
Devuelve el catálogo completo de estados con sus transiciones permitidas (allowed_transitions: string[]). Lo consume el frontend para saber qué botones mostrar en cada expediente.
GET /cases/:id/lifecycle/history
Historial de transiciones del expediente ordenado cronológicamente. Incluye from_state, to_state, trigger_type, triggered_by_name, justification y source_act_type.
POST /cases/:id/lifecycle/transition
Ejecuta una transición manual. Body: { to_state_code: string, justification: string }.
justification es obligatorio — el endpoint rechaza la petición si está vacío.
Requiere que el usuario sea creador, abogado responsable, socio o admin del caso.
Todos los endpoints requieren el header Authorization: Bearer <supabase-jwt> y validan acceso por caso antes de actuar. El cliente de servicio (service_role) se usa solo internamente; las peticiones externas siempre pasan por la guardia de autenticación.

Transición automática y fast-forward

El pipeline de extracción crea todo expediente nuevo en estado INICIADO. Ningún destino de ACT_TO_STATE es adyacente a INICIADO en el grafo (un traslado de demanda implica que la demanda ya fue admitida y que la notificación ya salió). Para no inventar estados en el historial ni saltear etapas procesales reales, transitionAuto calcula el camino más corto entre el estado actual y el destino, y registra cada salto como una fila AUTO independiente.

Ejemplo — documento con TRASLADO_DEMANDA sobre expediente nuevo

INICIADO → ADMITIDO       AUTO · TRASLADO_DEMANDA
ADMITIDO → NOTIFICANDO    AUTO · TRASLADO_DEMANDA
NOTIFICANDO → EN_TRASLADO AUTO · TRASLADO_DEMANDA

Estados bloqueados para passthrough automático

El algoritmo BFS excluye cuatro estados como nodos intermedios. Son declaraciones judiciales o acuerdos entre partes: inferirlos de un documento sería inventar un hecho procesal. Solo se pueden alcanzar como destino final, nunca como paso de camino.
